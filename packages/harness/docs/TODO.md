## 核心原则

1. 先理解架构，再写代码
   - 不要看到一个 TODO 就立即实现。
   - 先理解模块职责、依赖方向、生命周期和数据流。
   - 先建立完整 TODO Task，再按照依赖关系逐步实现。

2. 严格遵守架构边界
   - 不随意改变已有架构设计。
   - 不为了实现某个功能而破坏模块职责。
   - 保持单向依赖。
   - 避免循环依赖。
   - 基础层不能依赖业务层。
   - 核心框架不能绑定具体业务实现。
   - 可替换能力优先通过 interface / contract / plugin 实现。

3. 优先设计稳定的抽象
   - 公共 API、Contract、Plugin、Task、Agent、Tool、Model 等核心抽象需要稳定、清晰。
   - 避免把具体实现泄漏到公共接口。
   - 避免让上层依赖第三方库的内部类型。
   - 如果一个实现未来存在多个实现方式，应优先定义清晰的抽象边界。

4. 优先复用，而不是复制
   - 相同逻辑只实现一次。
   - 不要为了通过测试复制一份逻辑。
   - 将真正稳定、具有语义意义的公共逻辑抽取出来。
   - 不要为了“复用”而过度抽象简单代码。

5. 保持代码简单
   - 不过度工程化。
   - 不为了未来可能存在的需求增加复杂抽象。
   - 优先使用简单、清晰、可读的 TypeScript。
   - 一个函数只负责一个明确的事情。
   - 一个模块有清晰的职责。
   - 避免巨大文件、巨大函数和万能 manager。

6. TypeScript 质量
   - 保持严格类型安全。
   - 避免 any、类型断言和隐式类型逃逸。
   - 优先通过类型设计解决问题，而不是运行时判断。
   - 公共 API 类型必须清晰。
   - 错误类型和边界情况需要明确。

7. 测试策略
   - 不需要为每一个简单函数机械地创建测试。
   - 优先测试核心行为、模块边界、状态变化、错误处理和关键集成路径。
   - 已有测试应作为行为约束，而不是为了让测试通过而修改生产代码。
   - 最终必须有一套完整测试验证整个核心流程。

8. 错误处理
   - 不吞异常。
   - 不使用空 catch。
   - 错误应该在合适的边界被处理。
   - 公共 API 对失败行为要有明确约定。
   - 不使用大量隐式 fallback 掩盖真正的问题。

9. 可维护性
   - 命名优先表达业务语义，而不是实现细节。
   - 避免缩写。
   - 避免隐藏副作用。
   - 避免过深的嵌套。
   - 优先让代码可以被另一个工程师快速理解。

## 执行流程

### Phase 1：理解项目

首先阅读：

1. PLUGIN_AGENT_FRAMEWORK_PLAN.md
2. 当前 src 目录
3. package.json / tsconfig
4. 已有测试文件
5. 现有类型、接口和入口文件

然后总结：
- 核心模块
- 模块职责
- 依赖关系
- 核心数据流
- 生命周期
- 当前缺失的实现
- 测试覆盖情况

这一阶段只分析，不急于修改代码。

### Phase 2：建立 TODO Task

创建一个完整的 TODO Task List。

Task 必须按照依赖关系排序，而不是按照文件顺序。

每个 Task 包含：
- 目标
- 涉及模块
- 前置依赖
- 实现内容
- 验证方式

优先完成底层 Contract → Core → Runtime → Adapter → Scenario 的依赖链。

### Phase 3：逐步实现

按照 TODO Task 从底层向上实现。

每完成一个重要模块：

1. 检查类型
2. 检查依赖方向
3. 运行相关测试
4. 修复问题
5. 再进入下一个模块

不要一次性生成大量未经验证的代码。

### Phase 4：集成验证

所有模块完成后：

1. 运行 TypeScript 类型检查
2. 运行完整测试
3. 检查 lint / build
4. 检查模块依赖
5. 检查公共 API
6. 检查是否存在重复实现
7. 检查是否存在不必要的抽象
8. 检查是否存在 TODO / FIXME / 临时实现
9. 检查错误处理
10. 检查测试是否覆盖核心流程

发现问题时直接修复，不要只报告问题。

### Phase 5：最终架构审查

以 Code Review 的方式重新检查整个项目：

- 是否违反设计文档？
- 是否出现循环依赖？
- 是否出现职责泄漏？
- 是否存在 God Object？
- 是否存在过度抽象？
- 是否存在重复代码？
- 是否把具体实现泄漏到核心层？
- 是否存在不必要的第三方依赖？
- 是否存在明显的扩展困难？
- 是否存在为了测试而设计的代码？
- 是否存在 Demo 化实现？

如果发现问题，在最终结束前直接修复。

## 修改原则

允许：
- 创建缺失的实现文件
- 补充必要的类型和接口
- 补充必要的测试
- 在不改变架构原则的情况下调整内部实现
- 为了正确的模块边界进行小范围重构

不允许：
- 没有充分理由重写整个项目
- 随意改变架构设计
- 创建大量没有实际价值的 abstraction
- 为每个小函数创建独立模块
- 为每个简单功能创建独立 package
- 为了通过测试修改正确的行为
- 用 any 绕过类型问题
- 用 mock/fake 掩盖真实实现问题
- 留下 TODO、FIXME、placeholder 或伪实现
- 把未来需求提前实现
- 引入没有实际必要的依赖

## 完成标准

只有同时满足以下条件才能认为任务完成：

- 架构设计中的核心功能全部实现
- 所有核心 TODO 完成
- TypeScript 类型检查通过
- Build 通过
- 完整测试通过
- 核心流程可以实际运行
- 模块职责清晰
- 依赖方向正确
- 没有明显重复实现
- 没有明显过度抽象
- 没有临时实现
- 公共 API 清晰稳定
