# Nova SDD 技术实施方案

本文定义首版目标契约。表、接口和事件均为待实现项。实施范围是需求优先的 Feature Spec，支持单任务执行、版本化审阅和验收。

## 产品入口

SDD（Spec-Driven Development，规格驱动开发）从项目 Chat 首页选择「Spec 模式」启动。选择模式只改变当前输入框的发送意图，输入内容、模型选择和当前页面保持在 Chat；发送首条 query 后，服务端在同一事务创建规格、专用会话并将该 query 作为首轮 Plan 生成输入入队。客户端直接进入与普通 Chat 同级的独立双栏工作台（`/specs/:id?projectId=…`），不经过规格创建表单。`/specs` 兼容入口转到选中 Spec 模式的新 Chat。用户先确认行为和实现方案，再从任务清单发起执行，最后按验收标准核对结果。项目可以有多份 Spec，每份 Spec 关联一个专用项目会话，关掉页面后可从项目会话列表继续；打开该会话时回到对应的 Spec 页面。

Kiro 的 Feature Specs 用 `requirements.md`、`design.md`、`tasks.md` 串起需求、设计和任务，并支持从任务清单启动执行。Nova 采用这三个产物，沿用自己的项目会话、Plan / Build 工具策略和 Run 生命周期。[Kiro Specs](https://kiro.dev/docs/specs/) · [Nova 会话和工具策略](chat-project-goal-ssh.md)

## 用户流程

| 步骤 | 用户看到的内容和操作                                                      | Nova 的行为                                                      |
| ---- | ------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 创建 | 在项目 Chat 输入框选择 Spec 模式，输入想实现的功能并发送首条 query | 原子创建 Spec、关联会话与首轮 Plan 输入，直接进入双栏工作台 |
| 需求 | 审阅用户场景、边界和验收标准，可直接编辑或要求 Agent 修订                 | 记录确认的需求版本。遇到会改变用户行为的歧义，通过会话提问       |
| 设计 | 审阅涉及的模块、数据流、错误处理和验证方式                                | 根据已确认的需求及代码生成设计。确认后生成任务清单               |
| 任务 | 查看依赖、验收项和验证命令，确认任务计划后选择「运行任务」                | 校验版本和依赖，将这次任务提交给现有 Run 队列，以 Build 策略执行 |
| 验收 | 查看各任务关联的 diff、运行记录及测试结果，补录人工检查并选择「验收规格」 | 校验当前版本的任务和验收项均有通过记录，保存本次验收的版本与时间 |

桌面左侧为 Spec Workbench，以带流向箭头的「需求 → 设计 → 任务 → 验收」四步流程导航；右侧复用现有 Chat 展示专用项目会话。中间的分隔条支持拖拽和键盘调整宽度并记住比例。窄屏通过页签切换会话和工作台。需求自动解析并高亮 AC 标题；任务展示依赖原因、当前状态和关联 Run，回执及控制台日志保留在右侧会话。验收页展示 AC 满足率矩阵、证据台账和冻结记录。规格审阅是产品层确认，文件写入和命令仍由现有工具审批策略授权。

工作台不展示规格切换、新建规格、AI 生成表单、版本历史、旧证据复核或导出控件。需求补充和 Agent 草稿生成通过右侧 Chat 完成。下文的版本与导出契约保留为内部持久化、并发控制和 API 能力，不作为当前产品界面的操作概念。

AI 生成与修订复用现有模型选择，支持已配置的 Gemini 等模型。项目尚未绑定工作区时，允许在 Spec 专用会话中以 Plan 讨论和修订草稿；Build 执行从任务卡片发起。

Agent 的 `nova.spec` skill 位于 `packages/tools/skills/spec/SKILL.md`，由 Harness 的 skills 插件加载。`spec_read` 读取本次 Run 固定的版本；`spec_update` 提交完整阶段草稿候选。宿主仅在 Run 成功结算、候选校验通过且来源版本仍为当前版本时创建新修订。Agent 不能通过这些工具确认阶段、采纳旧证据或完成最终验收。

## 规格格式

| 导出文件          | 内容                                           | 规则                                                                             |
| ----------------- | ---------------------------------------------- | -------------------------------------------------------------------------------- |
| `requirements.md` | 用户场景、范围、验收条件                       | 每条验收条件有稳定 ID，例如 `AC-01`，用「当 [条件] 时，系统应 [可观察结果]」描述 |
| `design.md`       | 受影响模块、接口与状态变化、异常路径、验证策略 | 关联确认的需求版本，按验收条件说明实现和验证办法                                 |
| `tasks.md`        | 任务 ID、目标、依赖、关联验收项、验证方法      | 每项任务都有可独立检查的结果，任务依赖无环，每条验收条件至少有一项验证任务覆盖   |

例如「会话导出」中的 `AC-01` 可以写成「当用户导出仍有下一页历史消息的会话时，下载的 Markdown 应包含全部历史消息并按原顺序排列」。设计说明如何沿现有游标读取后续页，任务 `T-02` 用包含多页消息的测试验证条数与顺序。用户可在任务行打开实际测试结果。

需求和设计以 Markdown 草稿编辑，任务清单使用结构化字段编辑并渲染成 Markdown。导出从服务端同一份规格生成三份文件，任务勾选从实际执行状态生成。

## 版本与任务状态

```mermaid
flowchart LR
    R["需求草稿"] -->|确认需求| D["设计草稿"]
    D -->|确认设计| T["任务草稿"]
    T -->|确认任务计划| B["任务执行"]
    B -->|任务与验收项通过| V["用户验收"]
    V -->|确认验收| C["已验收"]
```

- **修订规格**。保存和确认都带上预期版本。修改已确认内容会产生新版本，并让该阶段及下游确认失效。原文档、任务结果与验收证据保留在旧版本里。重新确认任务计划后，可显式将仍适用的证据带入新版本，记录来源和复核人。旧任务的勾选状态不会自动带入。
- **执行任务**。只有当前计划已确认、依赖均通过且会话可接收该任务时才能开始。每份 Spec 同时只执行一个任务。服务端固定本次运行所用的规格版本与任务，执行期间暂停修改规格和任务计划。准备、执行、审批等待和取消分别沿用 Run 的状态投影。
- **确认结果**。Run 正常结束且任务验证全部有证据时，任务进入「通过」。验证失败或缺少证据时，任务进入「待验证」，并显示原因和检查项。自动证据需关联本次 Run 的工具结果，人工检查需显式记录确认人和结论。Agent 在聊天中说「完成」不会改变任务状态。
- **恢复任务**。失败、取消或超时后，保留已产生的工作区修改和运行记录。用户核对后可以重试；远程操作结果未知时进入「待核实」，优先查原操作回执，或由用户核对工作区并记录处理结论。核实前服务端拒绝创建新尝试。
- **最终验收**。必需任务均通过且当前版本的每条验收条件有证据时，用户可验收。验收记录绑定规格版本和证据。后续修订开启新一轮验收。

## Nova 接入

| 层     | 首版落点                                                                                                                                           |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Client | 在 `apps/nova-client/src/features/specs` 放项目规格列表、规格面板和操作。复用项目会话与 Run 面板。通过现有查询缓存获取规格快照，SSE 通知后重新读取 |
| Server | 在 `apps/nova-server/src/modules/specs` 负责规格归属、版本、确认、任务和验收。Fastify 契约进入现有 OpenAPI / Orval 生成流程                        |
| Run    | 复用 `apps/nova-server/src/modules/runs` 的队列、执行宿主、审批和 checkpoint。运行配置携带 `specId`、`specRevision`、`taskId`；普通 Run 无此上下文 |
| 持久化 | PostgreSQL 保存 Spec、不可变版本、按版本绑定的任务尝试和证据。Markdown 导出是这些数据的投影。Runner / SSH 负责读取和执行项目代码                   |

首版由服务端保存规格，便于远程执行环境离线时继续审阅，并让确认、版本校验和任务入队共享数据库事务。代价是规格历史在 Nova 内维护，项目 Git 通过手动导出获取 Markdown。

### PostgreSQL 表结构

首版新增三张表。项目归属沿用 `projects.owner_user_id`。创建 Spec 时同时创建项目会话，校验其项目、用户归属和会话类型。

| 表                   | 主要字段                                                                                                                            | 键与用途                                                                                                    |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `specs`              | `id`、`project_id`、`conversation_id`、`title`、`current_revision`、`created_at`、`updated_at`                                      | `id` 为 UUID 主键。会话 ID 唯一。按 `(project_id, updated_at, id)` 索引项目列表                             |
| `spec_revisions`     | `spec_id`、`revision`、`requirements_md`、`design_md`、`task_plan`、`reviews`、`evidence`、`acceptance`、`created_by`、`created_at` | 主键 `(spec_id, revision)`，引用 `specs`。Markdown 用 `text`，任务计划、确认、证据与验收用各自的 JSONB 字段 |
| `spec_task_attempts` | `id`、`spec_id`、`revision`、`task_key`、`pending_input_id`、`request_key`、`created_at`、`released_at`、`resolution`               | 复合外键引用规格版本。队列输入 ID 唯一，`(spec_id, request_key)` 唯一。用 `pending_inputs.run_id` 找到 Run  |

**版本与确认。** `task_plan` 按显示顺序保存任务 ID、标题、目标、依赖和检查项。检查项记录稳定 ID、验证方法及覆盖的 `AC-xx`。保存时校验任务和检查项 ID、依赖存在且无环，以及验收条件覆盖。编辑时插入新的版本并更新 `specs.current_revision`，正文和任务计划随版本固定。确认记录含确认人、时间和来源版本，新版本继承未受影响阶段的确认。

**排队与互斥。** 启动时沿用会话行锁，再锁定 Spec。先按幂等键查询原尝试，同键同参数返回原记录，同键异参数返回冲突。新请求在同一事务校验当前版本、任务 ID、确认记录、依赖和会话准入，然后创建 `pending_inputs` 和尝试记录。对 `spec_id` 建立 `WHERE released_at IS NULL` 的部分唯一索引，覆盖 Run 还没创建的排队窗口。队列拒绝、移除或 Run 到达已知终态时释放执行占用。结果未知时保留占用，在 `resolution` 记录核实结论后释放。

**状态和验收。** 根据尝试、队列、Run 和版本证据计算任务状态。`evidence` 保存证据 ID、任务和检查项 ID、结论、记录人及时间。自动证据引用本次尝试和工具结果，跨版本采纳记录原版本、证据 ID 和复核人。服务端锁定 Spec 后校验这些引用，再按来源去重并追加证据。最终验收也在同一锁下核对当前版本，并记录验收人、时间和采用的证据 ID。

这个结构适合按 Spec 整体读取。JSONB 里的任务、检查项和证据引用由服务端校验。证据只存结论与来源，完整工具输出留在现有运行记录。跨项目按任务或证据聚合需要展开 JSONB。

**记录保留。** 现有会话删除会物理删除队列输入和 Run。对关联规格的会话，单独删除请求返回冲突，清理走规格的删除流程。清理前先结算排队、运行和待核实的尝试，再按依赖顺序删除规格数据和会话数据。

### 迁移和数据契约

- 在 `apps/nova-server/database/schema/` 添加三个 `*.table.ts` 并从 `schema/index.ts` 导出。主 ID、项目 ID、会话 ID、用户 ID 和队列输入 ID 用 UUID。时间用 `timestamptz`，版本用正整数。除尚未产出的 `design_md`、`acceptance`、`released_at` 和 `resolution` 外，上表字段均必填。初始版本为 1，`requirements_md` 可以为空字符串，`task_plan` 和 `evidence` 初始为 `[]`，`reviews` 初始为 `{}`。
- 数据库约束包括 `UNIQUE (conversation_id)`、版本表到 Spec 的外键、尝试表到版本表的复合外键、队列输入唯一、请求键唯一，以及未结算尝试的部分唯一索引。尝试历史增加 `(spec_id, revision, task_key, created_at, id)` 索引。`current_revision` 在创建和修订事务内随版本记录一起写入。
- Zod 契约在服务端定义。任务计划为 `Task[]`，每项含 `key`、`title`、`objective`、`dependsOn` 和 `checks`。检查项含 `key`、`criterionIds`、`label` 和 `method`。方法为 `{ kind: "manual" }` 或 `{ kind: "command", command, args, cwd? }`，命令参数与现有 `bash` 工具一致。首版所有任务必做，每项至少一个检查。
- 需求在 `## 验收条件` 小节中用 `### AC-01` 形式声明验收项。按 Markdown 标题节点解析，直到下一个二级标题，代码围栏中的标题文字不计入。确认需求时至少有一项且 ID 唯一。确认任务计划时校验同版本任务依赖、检查项引用和验收覆盖。保存草稿允许覆盖不全，确认前必须通过全部检查。
- 初始输入限制为单份 Markdown 128 KiB、每版 50 项任务、每项 10 条检查，人工说明最多 2,000 字符。证据每次尝试和每条检查最多记录一次自动通过，重复工具结果按来源去重。输出原文通过运行记录查看，列表只取摘要和尝试状态。

### API 契约

以下路径均从 `/api` 起。项目范围路径记作 `P = /projects/:projectId/specs`，规格路径记作 `S = P/:specId`。全部接口使用现有认证、成功信封和错误信封。任何读取或写入都验证项目未删除、用户归属、Spec 属于项目，以及子资源属于 Spec。未归属资源统一返回 404。

| 方法和路径                             | 入参                                                                                  | 成功响应                                                                                       |
| -------------------------------------- | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `GET P`                                | `limit?`、`cursor?`                                                                   | 200，摘要分页。按 `updated_at DESC, id DESC` 取下一页                                          |
| `POST P`                               | `{ title, brief, startGeneration?, configuration? }`，请求头 `Idempotency-Key` | 201，Spec 与项目会话标识。初始草稿包含 `brief`；`startGeneration=true` 时，同事务创建以原始 query 为消息正文的 Plan 输入与唤醒 Job。重放返回同一 Spec |
| `GET S`                                | `revision?`，省略表示当前版本                                                         | 200，当前版本号、所选版本正文、确认、任务状态、验收及关联 Run 摘要                             |
| `PATCH S/draft`                        | `{ expectedRevision, stage, content }`                                                | 200，新版本快照。同内容保存返回当前快照                                                        |
| `POST S/reviews/:stage`                | `{ expectedRevision }`                                                                | 200，写入该阶段确认，返回快照                                                                  |
| `POST S/generations`                   | `{ expectedRevision, stage, instruction?, configuration? }`，请求头 `Idempotency-Key` | 202，队列输入 ID，Run 通过现有会话事件关联                                                     |
| `POST S/tasks/:taskKey/attempts`       | `{ expectedRevision, configuration? }`，请求头 `Idempotency-Key`                      | 202，尝试 ID、队列输入 ID、可空的 Run ID                                                       |
| `GET S/attempts`                       | `revision`、`taskKey?`、`cursor?`                                                     | 200，尝试历史及证据摘要，按创建时间和 ID 倒序                                                  |
| `POST S/evidence`                      | `{ expectedRevision, evidenceId, taskKey, checkKey, source }`                         | 200，已记录的证据和当前任务状态                                                                |
| `POST S/attempts/:attemptId/reconcile` | `{ expectedRevision, note? }`                                                         | 200，已结算的尝试。无法证实执行已终止时返回 409                                                |
| `POST S/acceptance`                    | `{ expectedRevision }`                                                                | 200，验收人、时间、版本和证据 ID                                                               |
| `GET S/export`                         | `revision?`                                                                           | 200，`{ revision, files: [{ name, content }] }`。三份 Markdown 由服务端生成                    |
| `DELETE S`                             | `expectedRevision`                                                                    | 200，完成规格及专用会话的事务清理                                                              |

`stage` 取 `requirements`、`design` 或 `tasks`，前两者提交字符串，任务提交 `Task[]`。生成和执行的 `configuration` 沿用现有会话模型选择，服务端分别固定 Plan 和 Build，使用会话的项目绑定。证据来源为 `manual` 或 `carried`。前者包含本次尝试 ID、结论和说明，后者包含同一 Spec 内的来源版本、证据 ID 和复核说明。自动证据由 Worker 写入。相同 `evidenceId` 和内容重复提交返回原证据，内容不同返回冲突。

格式和内容校验用 400，状态或并发冲突用 409。前端按 `details.reason` 处理 `SPEC_REVISION_STALE`、`SPEC_REVIEW_REQUIRED`、`SPEC_DEPENDENCY_UNMET`、`SPEC_BUSY`、`SPEC_ACCEPTED`、`IDEMPOTENCY_KEY_REUSED` 和现有 `EXECUTION_OUTCOME_UNKNOWN`。过期响应包含 `currentRevision`。同幂等键的重放先比较请求，再检查当前版本，避免原请求已成功时误报过期。确认和验收的重复请求返回原记录。

### 状态转换和读模型

| 操作或事实   | 前置条件                                                  | 结果                                                                                              |
| ------------ | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 保存阶段内容 | 当前版本匹配，且无未结算的任务尝试                        | 创建下一版本，保留上游确认，清除本阶段及下游确认，初始化证据与验收。下游正文作为待复核草稿保留    |
| 确认阶段     | 当前版本匹配，上游已确认，本阶段通过内容校验              | 写入一次确认，开放下一阶段。确认任务后开放任务执行                                                |
| 开始任务     | 计划已确认，依赖任务已通过，本任务可运行，会话空闲        | 创建队列输入和尝试。快照状态为 `queued`                                                           |
| Worker 领取  | 队列输入关联有效尝试                                      | 创建 Run。运行、等待审批、暂停和取消中状态来自 Run                                                |
| 已知终态     | 队列移除、拒绝或 Run 到达已知终态                         | 释放占用。失败、取消、超时显示对应结果，允许重试。Run 成功时进入 `passed` 或 `needs_verification` |
| 结果未知     | Run 进入 `cancelled_unconfirmed` 或存在未结算的未知副作用 | 显示 `needs_reconciliation`，保留占用                                                             |
| 验收当前版本 | 无未结算尝试，全部任务和验收项通过                        | 保存验收记录。当前版本冻结执行和证据写入，修改规格会产生可执行的新版本                            |

任务成功以最新一次尝试为准。该 Run 成功且每个检查均有通过证据时，任务为 `passed`。人工检查的有效结论取本次尝试最新一条。跨版本采纳只接受已通过的旧任务证据，目标检查的方法与验收条件须经用户逐条复核。没有新尝试时，全部检查均已复核的任务也可通过。产生新尝试后按该尝试重新计算。已通过的任务与已验收的版本通过修订开启新一轮执行。

### 运行接入与事务

1. **入队。** 复用会话现有的输入入队和唤醒逻辑。跨模块写事务的加锁顺序为会话、已有 Run（如果本事务需要）、Spec。持会话与 Spec 行锁后检查归属、预期版本、确认、依赖及活动输入。入队、尝试写入、输入事件和唤醒 Job 一起提交。专用会话中的普通消息沿用只读 Plan，任务运行中只接受现有 Decision 回复、取消与队列移除。目标循环和调整方向入口在此会话禁用，服务端同时校验。
2. **领取和恢复。** `RunRepository` 通过 `pending_inputs.id` 找到尝试，读取精确版本和任务。将 `{ specId, revision, taskKey, attemptId }` 作为服务端运行元数据持久化进 checkpoint，并在恢复时据此构造同一份上下文。该元数据从事务内已验证的尝试生成。沿用现有 Worker fence、环境准入、工具审批和执行预算。
3. **生成草稿。** 生成输入带服务端写入的 `{ specId, baseRevision, stage }`。通过宿主注册的结构化输出工具收集候选内容，工具只返回结构化结果，由现有 Run 结果持久化。Run 成功结算时按阶段校验候选结果，在同一事务内以 `baseRevision` 为条件写入新版本。版本已前移时保留该 Run 的候选结果，用户可复制到当前草稿。校验失败显示生成错误，保留原规格。
4. **提取自动证据。** 在 Run 成功结算时从持久化工具调用和结果匹配计划中的命令、参数和解析后的工作目录。验证安排在实现改动结束后。自动证据只采纳最后一个非验证写操作结束后发起的匹配命令，同一检查以最后一次调用的结果为准。仅接受已知结果且退出码为 0，保存尝试 ID、工具操作 ID、检查项 ID 和时间。缺少有效结果时显示待验证，用户可以重试，也可亲自执行相同检查并录入明确标注为人工的结果。
5. **终态结算。** 在现有 Run 终态事务及队列移除、拒绝路径接入尝试释放，按 `attemptId` 幂等写入。证据和验收的读改写均使用 Spec 行锁。Spec 元数据变更和对应会话事件在同一事务提交。
6. **核实未知结果。** 沿用 Run 的环境阻塞语义。查询原 Runner 操作回执，或由执行宿主确认原操作已经停止，再由用户核对工作区并记录结论。回执查询在事务外完成，提交时重新校验尝试、Run 与回执目标。确认后在同一事务记录 `resolution`、将 Run 结算到已知终态并释放尝试。历史回执保留，Run 结算不生成通过证据。缺少执行已停止的证据时继续阻塞，尤其是 SSH 断线后无法确认原命令是否仍运行的场景。恢复流程始终沿原操作核实。

新增内部输入元数据须与普通会话提交 schema 分离，Agent 草稿及证据写入只接受匹配的 Run 类型。锁定 Spec 后的用例不得逆向获取会话锁。删除沿专用会话入口执行整份 Spec 的清理事务。已部署迁移保持原样，新增迁移先部署到数据库，再启用 Server 和 Worker 的新写入路径。

### Client 接入

- 项目页加载规格列表，选择规格后打开关联的项目会话和规格面板。面板状态以 `GET S` 的快照为准，当前版本和历史版本可切换。历史版本为只读。使用查询键按项目、规格和版本隔离缓存。
- 需求和设计使用 CodeMirror 6 与 `@codemirror/lang-markdown`，从编辑态切到预览态时复用现有 `react-markdown` 和 `remark-gfm` 渲染规则。任务使用结构化表单。编辑器按打开面板时加载。保存携带编辑开始时的版本号，409 时保留本地文本，提示刷新版本后再合并。
- 继续使用会话 SSE。在现有事件契约中加入轻量 `spec.changed`，只含 Spec ID、版本和变更类别。活动 Run 的进度仍来自既有事件。收到规格事件后按键刷新快照和尝试历史，断线重连及页面重新打开时重新获取快照。导出时客户端用返回的 Markdown 创建下载文件。
